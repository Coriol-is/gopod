# Deployment evidence — private authentication handoff

## Payload and verification

Application `01c18fe2b484a7aad3dd6d713942453360eca161` (PR #53).
Group login requests cannot start a public authentication flow. The configured
owner may request a private DM confirmation bound to a registered target group;
only private owner confirmation starts its separate runtime authentication.
URL/device codes/status remain private. Display in an owner DM does not change
the target folder or `TierRegistered` and does not copy owner CLI homes.

OAuth input and active-flow credential quote/reply metadata bypass persistence,
media work and model prompts. SDK-registered `/login` commands also omit message
persistence. Raw CLI stdout/errors are not rendered or logged; controlled local
status replaces substring-based success. Dedicated bounded private sends have
no public fallback/raw SDK error logging. Historical messages are not erased.

## Limits and separate isolation work

A20 real owner-DM confirmation/login/client visibility remains pending until
observed by actual users. Startup/container health or fake API success does not
qualify that UI, account identity or model/quota availability. No automatic
reauthentication, token revocation, historical deletion or Telegram rights change
was issued by rollout. Interactive cleanup closes attachment/EOF; process-group
termination and upstream token revocation are not verified by that operation.

This hotfix closes auth-delivery/input-retention risks, not the full container
boundary. The [CP-020 audit](../research/2026-10-25-personal-group-isolation-audit.md)
records remaining vault/global-env/bind-source/account-service exposure.
Its [plan](../superpowers/plans/2026-10-25-personal-group-container-isolation.md)
and draft group/channel agent policies are not applied by this rollout. Existing
group credentials/configuration were not silently migrated or revoked.
